## Architecture rules
- Business rules for metrics (success rate, rerun dedup, failure grouping, coverage, projection, cross-project aggregation) live as pure functions in `src/lib/metrics.ts` with tests in `metrics.test.ts` — keeps rules verifiable without UI.
- Projects (with API/UI repo owner+name+branch; legacy URL columns are deprecated fallbacks) and dashboard widgets live in the database; widget rows with `project_id` null belong to the overview. No rows = code defaults, materialized on first edit.
- Failure/flaky panels read test-stability-30d, failure-reasons-30d and failure-lifecycle as primary sources (API+UI grouped, `buildSpecial` in useDashboard); history.json only as labeled per-product fallback.
- GitHub JSON (`quality-hub/*.json` via Contents API) is fetched only in `src/lib/sources.functions.ts` (authenticated server fn, `GITHUB_TOKEN` server secret, host allowlist). Administrators synchronize into MongoDB; charts read stored snapshots, scheduled executions and weekly evolution. Polling occurs every 5 minutes while a dashboard is open; it is not a standalone scheduler. Missing sources are reported without substituting mock data.
- The main administrator is configured on the backend; additional administrator and viewer accounts are created by an administrator and stored in MongoDB. Only administrators may edit; legacy editor accounts are read-only. Enforce roles on the backend; public signup is disabled; app pages live under `src/routes/_authenticated/`.
- Failure nature (who must act: product bug, environment, test data, automation, investigate) is derived in `classifyFailures` (`src/lib/metrics.ts`) from the first line of the error message, never from stack/test code; runs with mass failure collapse into one environment incident. API and UI use the same rules (`buildNature` in useDashboard).
- API coverage uses the production contract (Swagger from the product `main`) as the minimum universe: each method + route + documented status is one condition, covered when a passed scheduled test exercised it (several tests of one condition count once); 5xx and 429 are outside the base. Every API project that publishes `quality-hub/api-swagger-coverage-current.json` (with `obligations`) enters the `contract_coverage` panel automatically (`endpointCoverage`/`contractSummary` in metrics.ts). UI coverage will use critical journeys defined with the POs, not a contract.
- Bugs come from Azure DevOps, read only in `sources.functions.ts` (`loadBugs`/`readAzure`) with the `AZURE_DEVOPS_PAT` server secret (Work Items read), host `dev.azure.com`, values escaped in WIQL. There is ONE global config (organization, project, root area, board team) in `app_settings` `_id:"azure-devops"`, edited by admins on the Bugs page — not per project, because the query covers every project. Bugs = type Bug under the root area, defeitos = Tasks tagged DEFEITO (same queries as the "Dash QA" Azure dashboard), PBIs (requirement category) only feed the bug ratio and board column load. Squad = first subarea below the root (`squadOf`). Admins sync into `bug_snapshots` (TTL 5 min, same refresh button); others read the snapshot. Summary, weekly burnup (Friday), distributions, board columns with WIP, time in state, squad comparison and bug ratio (bugs ÷ (bugs + PBIs) created in period) are pure functions in `metrics.ts`. The overview has two tabs: Automação and Bugs (`?aba=bugs`).
- Global period/origin filters live in `FiltersProvider` (`src/data/useDashboard.tsx`).
- App version constant is `APP_VERSION` in `src/components/dash/AppShell.tsx`; bump it on meaningful changes.
- Visual follows the Conecta Design System (github.com/Conecta-ag/conecta-DS, branch hml): tokens are vendored in `src/conecta-tokens.css` and mapped to Tailwind/shadcn names in `src/styles.css`; use those classes or `--conecta-*` tokens, never hardcoded colors. Theme is set by `data-conecta-theme` on `<html>`.
